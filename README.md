# Yaksit Pixel Battle

Real-time пиксельная доска с системой **раундов**: посетители ставят пиксели строго из палитры активного раунда с кулдауном, а администратор управляет раундами, холстом, модераторами, бэкапами и откатами.

## Возможности

- **Раунды** (`draft` → `active` → `finished`): у каждого раунда своё название, время начала/окончания, размер холста, кулдаун, фон и палитра разрешённых цветов. Одновременно активен только один раунд.
- **Автозапуск и автозавершение по расписанию**: сервер сам каждые несколько секунд проверяет раунды - завершает истёкший активный и запускает самый ранний подходящий черновик (`starts_at` уже наступил, `ends_at` ещё не прошёл). Просроченный черновик (тот, у которого уже прошёл `ends_at`) сам никогда не запустится - его нужно поправить или удалить вручную.
- **Дублирование и удаление черновиков** в админке: «Дублировать» открывает редактор нового черновика с настройками исходного раунда и безопасными будущими датами (ничего не пишется в БД, пока не нажать «Сохранить»); «Удалить» доступно только для черновиков и требует подтверждения с названием раунда.
- Палитра цвета - серверное правило: клиент не может поставить пиксель цветом вне палитры активного раунда, даже отправив запрос вручную.
- Публичный **архив** завершённых раундов (`/archive`) с превью и постоянными ссылками на каждый раунд.
- Обратный отсчёт, статус раунда («скоро начнётся» / «идёт» / «завершён»), счётчик онлайна и число поставленных пикселей - прямо на главной странице, обновляются в реальном времени без перезагрузки.
- Кнопка «Поделиться»: PNG холста через Web Share API (с фолбэком на скачивание) + постоянная ссылка на архив для завершённых раундов.
- Мобильная шлифовка: компактная палитра, заметный индикатор кулдауна, safe-area отступы под чёлку/жесты iPhone, пинч-зум и перетаскивание холста.
- Синхронизация холста через Socket.IO; анонимные подписанные идентификаторы пользователей.
- Админ-панель с CSRF-защитой, сессиями и ролями модераторов; управление раундами (создать черновик, изменить, запустить, завершить) с подтверждением опасных действий.
- Снапшоты, ZIP-таймлапс, экспорт/импорт и откат области - работают в рамках активного раунда.
- **Полный бэкап игры и безопасное восстановление**: версионированный JSON-экспорт всех раундов, пикселей, истории, снимков и архивов (с PNG в base64) из согласованного snapshot БД; строгая валидация перед восстановлением и восстановление одной транзакцией с откатом при любой ошибке. Никогда не включает сессии, модераторов, пароли или иные данные доступа.
- PostgreSQL и Docker Compose.

## Быстрый запуск для разработки

```bash
docker compose -f docker-compose.dev.yaml up --build
```

Откройте `http://localhost:8080`. Значения в dev Compose предназначены только для локального запуска.

## Создание первого раунда

Сразу после первого запуска раундов ещё нет - холст пуст, а на главной странице будет написано «Нет раунда» с пояснением, что рисование недоступно.

1. Откройте `/admin/login` и войдите как `admin` (пароль из `ADMIN_PASSWORD`).
2. Перейдите во вкладку **«Раунды»** → **«+ Новый раунд»**.
3. Заполните название, время начала/окончания, размер холста, кулдаун, цвет фона и палитру (минимум один валидный hex-цвет; пустая или невалидная палитра не сохранится).
4. Сохраните черновик. Дальше можно либо нажать **«Запустить»** вручную и подтвердить, либо просто дождаться времени `starts_at` - сервер сам активирует раунд по расписанию (проверка каждые ~15 секунд). В любом случае раунд станет единственным активным, все подключённые клиенты обновятся мгновенно, без перезагрузки.
5. Когда раунд пора завершать - нажмите **«Завершить»** и подтвердите, либо дождитесь `ends_at` (тоже автоматически). Финальное состояние холста сохранится в архиве (`/archive`) без возможности случайно потерять его при старте следующего раунда.
6. Черновик можно **«Дублировать»** (открывается редактор новой копии с теми же настройками и безопасными будущими датами) или **«Удалить»** (только для черновиков, с подтверждением по названию).

Если у черновика уже прошёл `ends_at`, а он всё ещё не запущен, панель пометит его «⚠️ Время истекло - измените даты или удалите» - такой черновик автозапуск сознательно пропускает.

## Production

1. Скопируйте `.env.example` в `.env` и заполните все переменные.
2. Укажите точный публичный адрес в `CORS_ORIGINS`.
3. Запустите:

```bash
docker compose up -d --build
```

Docker healthcheck использует `/ready`; перед контейнером должен стоять HTTPS reverse proxy.

### Переменные окружения

| Переменная | Назначение |
| --- | --- |
| `NODE_ENV` | `production` в проде, `development` локально |
| `PORT` | Порт, который слушает Node.js-сервер |
| `CORS_ORIGINS` | Список разрешённых origin'ов через запятую (используется и для CORS, и для Socket.IO) |
| `DB_USER`, `DB_PASSWORD`, `DB_HOST`, `DB_PORT`, `DB_NAME` | Подключение к PostgreSQL |
| `ADMIN_PASSWORD` | Пароль мастер-админа (логин `admin`) |
| `SESSION_SECRET` | Секрет для подписи сессий/cookie |
| `ROUND_SYNC_INTERVAL_MS` | Необязательная. Как часто (в мс) сервер проверяет расписание раундов - автозавершение истёкшего активного и автозапуск подходящего черновика. По умолчанию `15000`. Уменьшается в интеграционных тестах для скорости; в проде трогать не нужно. |
| `BACKUP_MAX_BYTES` | Необязательная. Максимальный размер JSON-файла бэкапа, в байтах - симметрично ограничивает **и экспорт, и восстановление**. По умолчанию `52428800` (50 МБ) - безопасное значение с запасом на base64 (раздувает бинарные данные примерно на треть). На восстановление ограничивает приём тела запроса и валидацию; на экспорт - точный UTF-8 размер уже сериализованного JSON проверяется до начала скачивания, так что успешно скачанный бэкап гарантированно проходит собственный лимит на восстановление. |
| `SHUTDOWN_TIMEOUT_MS` | Необязательная. Максимум миллисекунд на graceful shutdown (SIGTERM/SIGINT), прежде чем сервер принудительно завершится с ненулевым exit code. По умолчанию `15000`. |

Модераторы создаются уже после запуска - через админ-панель (пароли хранятся в виде bcrypt-хэшей).

### Liveness, readiness и graceful shutdown

**`GET /health`** - liveness. Дешёвая проверка, что процесс жив: не обращается к PostgreSQL и не проходит через сессии. `200 {"status":"ok"}`, пока сервер работает; `503 {"status":"shutting_down"}` с первой же миллисекунды после получения SIGTERM/SIGINT.

**`GET /ready`** - readiness. `200 {"status":"ready"}` только когда приложение реально готово обслуживать клиентов: инициализация БД (`initDatabase()` - миграции и загрузка состояния раундов) полностью завершена, сервер не в процессе graceful shutdown или восстановления из бэкапа, и PostgreSQL отвечает на дешёвый `SELECT 1`. Иначе - `503 {"status":"not_ready"}`; текст ошибки PostgreSQL наружу никогда не уходит, только в лог сервера. Docker healthcheck (`docker-compose.yaml`) использует именно этот эндпоинт, поэтому контейнер считается healthy только после полной готовности приложения, а не просто после старта процесса.

**Graceful shutdown.** SIGTERM и SIGINT запускают единый идемпотентный обработчик (повторный сигнал во время уже идущего shutdown логируется и игнорируется - выбран как самый простой безопасный вариант). Последовательность:

1. Синхронно, немедленно - `/health` и `/ready` тут же начинают отвечать соответствующим статусом; вход для новых игровых мутаций закрывается через тот же gate (`activeGameOps`/`enterGameOp`/`exitGameOp`/`withGameOp`), что уже использует backup restore - никакого второго независимого механизма.
2. Все фоновые `setInterval` (снимки холста, синхронизация расписания раундов, очистка `pixel_history`) останавливаются, чтобы не запустить новую мутацию.
3. Сервер дожидается уже начатых игровых операций целиком - SQL-запись, перезагрузку состояния раунда и рассылку Socket.IO-событий, - а если прямо сейчас выполняется восстановление из бэкапа, дожидается и его полностью. `restore`'s `finally` при этом **никогда** не открывает gate заново, если shutdown уже начался - restore и shutdown отслеживаются раздельными флагами (`restoring` и `shuttingDown`), а вход закрыт, пока установлен хотя бы один из них.
4. Клиентам рассылается событие `server_shutdown`, все Socket.IO-соединения принудительно закрываются, затем закрывается HTTP-сервер.
5. Последним закрывается пул PostgreSQL (`pool.end()`).

Всё это ограничено общим таймаутом `SHUTDOWN_TIMEOUT_MS` (по умолчанию 15 секунд, для Docker `docker-compose.yaml` задаёт `stop_grace_period: 20s`, чтобы Docker не прислал SIGKILL раньше). Штатное завершение выходит с кодом `0`; если shutdown не уложился в таймаут, сервер логирует ошибку, делает best-effort принудительную зачистку ресурсов и выходит с кодом `1`.

## Миграция существующей БД на систему раундов

Если в базе уже накоплен холст без раундов (старая версия), при первом запуске обновлённого сервера выполняется **безопасная идемпотентная миграция**:

- к таблицам `pixels`, `pixel_history`, `snapshots` добавляется колонка `round_id`;
- если в них есть данные без раунда, автоматически создаётся архивный завершённый раунд «Архив: холст до системы раундов» с прежними настройками холста и стандартной палитрой;
- все существующие пиксели, история и снимки переносятся в этот раунд (`UPDATE ... SET round_id = ...`) - **ни одна строка не удаляется**;
- для этого раунда сразу рендерится PNG-превью и кладётся в архив, так что прежнее состояние холста сразу доступно на `/archive`;
- первичный ключ `pixels` переносится на `(round_id, x, y)`, чтобы холст каждого раунда был независим.

Миграция безопасно перезапускается при каждом старте сервера: если данные уже перенесены, повторных изменений не происходит.

## Полный бэкап игры и восстановление

Это **не** `pg_dump` и не полный снимок базы данных - только игровой прогресс. Находится в админке во вкладке **«Система»**.

**Что входит в бэкап:** раунды, пиксели, история пикселей, снимки и архивы раундов (включая PNG-превью, без потерь - в base64).

**Что никогда не входит:** сессии, модераторы и их пароли/хэши, анонимные cookie-идентификаторы пользователей (таблица `users`), устаревшая таблица `settings`, `admin_logs`, любые переменные окружения и секреты.

### Формат файла

```json
{
  "format": "yaksit-pixel-battle-game-backup",
  "version": 1,
  "exported_at": "2026-01-01T00:00:00.000Z",
  "data": {
    "rounds": [...],
    "pixels": [...],
    "pixel_history": [...],
    "snapshots": [{ "id": 1, "round_id": 1, "data_base64": "...", "created_at": "..." }],
    "round_archives": [{ "round_id": 1, "preview_base64": "...", "pixel_count": 10, "created_at": "..." }]
  }
}
```

### Скачать бэкап

Кнопка **«Скачать бэкап игры»** во вкладке «Система» → GET-запрос на admin-only эндпоинт `/admin/backup/export` (ответ всегда с `Cache-Control: no-store`, чтобы админский бэкап не осел в кэше браузера или прокси). Все таблицы читаются из одной транзакции с `REPEATABLE READ` изоляцией, поэтому связанные данные (например, раунд и его архив) гарантированно относятся к одному и тому же моменту времени, даже если игра продолжается прямо во время экспорта.

Лимит `BACKUP_MAX_BYTES` действует **симметрично** и на экспорт: точный UTF-8 размер уже сериализованного JSON проверяется до начала скачивания. Если бэкап превышает лимит, сервер не отдаёт частичный файл, а отвечает `413` с объяснением, что лимит нужно увеличить через переменную окружения `BACKUP_MAX_BYTES`. Это гарантирует, что **любой успешно скачанный бэкап заведомо пройдёт собственный лимит на восстановление** - сервер никогда не выдаст файл, который сам же не сможет восстановить.

### Восстановить из бэкапа

1. Во вкладке «Система» выберите JSON-файл кнопкой **«Выбрать файл бэкапа»**.
2. Нажмите опасную кнопку **«ВОССТАНОВИТЬ ИГРУ ИЗ ФАЙЛА»**.
3. Подтвердите предупреждение о полной замене текущих игровых данных.
4. Введите слово `ВОССТАНОВИТЬ` для окончательного подтверждения.

Запрос уходит на `POST /admin/backup/restore` (admin-only, обязательный CSRF-токен в заголовке `X-CSRF-Token` - не через Socket.IO). Перед любыми изменениями в БД файл полностью проверяется: формат и версия, допустимые поля и типы каждой таблицы, ссылочная целостность между раундами/пикселями/историей/снимками/архивами, ограничения размеров (байты и количество строк), корректность base64 и то, что бинарные данные снимков/архивов действительно являются PNG (проверяется сигнатура файла), а также инварианты раундов - включая **не более одного активного раунда**. Валидация v1-формата строгая: на верхнем уровне допускаются только `format`/`version`/`exported_at`/`data`, в `data` - только пять игровых массивов, а в записи каждого массива - только документированные поля; любое незадокументированное поле отклоняется понятной ошибкой, а не молча игнорируется. Каждый раунд в бэкапе проверяется по тем же границам, что и обычное создание/редактирование раунда через API/админку (`normalizeRoundInput` в `lib/rounds.js`): `canvas_size` от 10 до 1000, `cooldown` от 0 до 3600 секунд, `ends_at` строго позже `starts_at`. Эти границы - общий источник истины (`lib/backup.js` импортирует их из `lib/rounds.js`, а не дублирует), так что restore не может создать раунд, который штатный API отклонил бы, - в частности, не может задать неограниченный `canvas_size`, ведущий к чрезмерному потреблению памяти при рендере PNG через Jimp. При этом исторические поля (`status`, `activated_at`, `finished_at`, `created_at`) сохраняются как есть - restore не прогоняет их через нормализацию создания нового раунда, которая нормализовала бы live-данные. Невалидный, слишком большой или неизвестного формата файл отклоняется, и **в БД ничего не меняется**.

Само восстановление выполняется одной транзакцией только над игровыми таблицами: `round_archives → snapshots → pixel_history → pixels → rounds` удаляются в этом порядке (сначала зависимые), затем вставляются в обратном порядке, после чего SERIAL-последовательности (`rounds.id`, `pixel_history.id`, `snapshots.id`) корректно сбрасываются на актуальный максимум - новые раунды и записи после восстановления не будут конфликтовать по id. При любой ошибке - весь откат, частично восстановленного состояния быть не может.

**Защита от гонки с уже начатыми операциями.** На время восстановления сервер включает глобальный режим обслуживания, но не полагается на один лишь флаг: любая функция, пишущая в игровые таблицы (`rounds`/`pixels`/`pixel_history`/`snapshots`/`round_archives` - размещение/удаление пикселя, очистка холста, создание/изменение/запуск/завершение/удаление раунда, ручные и фоновые снимки холста, автозапуск/автозавершение по расписанию, фоновая очистка старой истории пикселей, импорт и откат области холста) сама входит в общий async-gate (счётчик активных операций + очередь ожидания) в самом начале своей работы, синхронно и без единого `await` между проверкой режима и стартом счётчика. Gate держится открытым для операции не только на время её SQL-запроса, а на весь жизненный цикл: до её собственной перезагрузки `roundState` и рассылки Socket.IO-событий (`init_data`, `pixel_update`, `round_updated` и т.п.) включительно - иначе операция, уже прошедшая проверку режима, могла бы разослать клиентам устаревшее состояние уже после того, как restore разослал верное. Функции, которые сами вызываются и вручную, и в фоне (например `finishAndArchiveRound`), не оборачивают себя в gate самостоятельно - его один раз вызывает каждый конкретный вызывающий код (ручной обработчик и авто-завершение по расписанию отдельно), что исключает как вложенный (двойной) вход в gate, так и пропуск части жизненного цикла. Restore перед стартом своей транзакции синхронно закрывает вход для новых мутаций и дожидается, пока все уже начатые операции не завершатся сами целиком - только после этого начинается транзакция, а вход остаётся закрытым до перезагрузки состояния раунда и рассылки нового `init_data`. Так операция, начатая долями секунды раньше restore, гарантированно либо успевает полностью завершиться и разослать своё (пока ещё корректное) состояние раньше, чем restore начнёт свою транзакцию, либо restore ещё не стартовал вовсе - но никогда не может продолжить работу или что-то разослать уже после того, как восстановленные данные разосланы клиентам. Новые действия во время восстановления получают понятную ошибку через `socket.use` (быстрый путь) или явный ответ, а не зависают. Гарантированное открытие входа в `finally` исключает "залипание" режима обслуживания при ошибке восстановления. Админский аудит-лог (`admin_logs`) осознанно вынесен за пределы gate - он не пишет в игровые таблицы и не влияет на `roundState`/рассылку, поэтому его порядок относительно restore не имеет значения для корректности.

## Тестирование

Юнит-тесты (`backend/test/*.test.js`) - чистые функции и SQL-запросы на моках клиента БД, без сети:

```bash
npm test --prefix backend
```

Интеграционные тесты (`backend/test/integration/*.test.js`) поднимают настоящий `server.js` отдельным процессом на изолированной тестовой БД PostgreSQL (своя БД на каждый тестовый файл, удаляется после теста) и требуют доступную БД:

```bash
DB_HOST=127.0.0.1 DB_USER=postgres DB_PASSWORD=postgres DB_PORT=5432 npm run test:integration --prefix backend
```

Они проверяют: автозапуск раунда по расписанию на чистой БД, что при нескольких подходящих черновиках (включая настоящую гонку двух параллельных транзакций) активируется ровно один, что просроченный черновик никогда не запускается сам, безопасность и идемпотентность legacy-миграции (старые пиксели без `round_id` не теряются и переносятся в архив), полный жизненный цикл раунда (разрешённый цвет принимается, цвет вне палитры отклоняется, а после завершения `round_archives` содержит PNG, реально отражающий финальное состояние холста), и полный цикл бэкапа - экспорт/изменение БД/восстановление с точным совпадением данных и PNG побайтово, что невалидный файл не меняет БД ни на строку, что оба эндпоинта admin-only и что восстановление требует CSRF, а также что сессии/модераторы/прочие данные доступа восстановлением не затрагиваются. Два отдельных теста гонки с restore используют переменные окружения, читаемые только тестовым сервером (в production не заданы - задержки нет): один (`TEST_GAME_OP_DELAY_MS`, пауза сразу после входа в gate, до записи в БД) удерживает `create_round` «в полёте», параллельно стартует restore и доказывает, что после restore в таблице `rounds` не остаётся ни одной "запоздалой" строки; второй, более строгий (`TEST_GAME_OP_POST_DB_DELAY_MS`, пауза ровно между коммитом записи в БД и перезагрузкой `roundState`/рассылкой событий) удерживает уже закоммиченный, но ещё не разосланный `start_round` и по факту проверяет весь жизненный цикл: restore ждёт не только SQL-запрос, а операцию целиком; клиент получает от неё ровно два `init_data` за всё время - сначала легитимный (раунд активен, потому что операция стартовала раньше restore и была вправе завершиться), затем от restore (соответствующий бэкапу) - и ни одного лишнего/устаревшего после; только что подключившийся клиент и таблица `rounds` в БД после restore совпадают с бэкапом побитово. Ещё один набор юнит-тестов проверяет, что бэкап с раундом вне границ обычного API (`canvas_size` < 10 или > 1000, `cooldown` > 3600, `ends_at` ⩽ `starts_at`) отклоняется валидацией до каких-либо изменений в БД. Отдельный интеграционный тест с намеренно маленьким `BACKUP_MAX_BYTES` проверяет, что экспорт, который превысил бы лимит, отклоняется `413` без частичного скачивания, а бэкап, укладывающийся в лимит, экспортируется как обычно.

`backend/test/integration/shutdown.test.js` проверяет liveness/readiness и graceful shutdown: структуру ответов `/health` и `/ready` на живом сервере; что `/ready` отвечает `503`, когда PostgreSQL недоступен (детерминированно имитируется через `POST /__test__/force-db-down` - маршрут регистрируется, только когда `NODE_ENV=test`, так что production-код от этого теста никак не зависит), а `/health` при этом остаётся `200`, потому что сам процесс жив; что SIGTERM дожидается уже начатой игровой операции (`TEST_GAME_OP_DELAY_MS`), её запись реально попадает в PostgreSQL, и только после этого процесс выходит с кодом `0`; что после начала shutdown новая мутация никогда не проходит и не попадает в БД (`TEST_SHUTDOWN_DELAY_MS` даёт тесту детерминированное окно понаблюдать состояние `shutting_down`, когда дожидаться нечего и обычный shutdown уложился бы в единицы миллисекунд); и главный race-тест - что shutdown дожидается уже выполняющегося restore целиком (`TEST_RESTORE_DELAY_MS`), restore получает свой полный успешный ответ до того, как процесс завершится, ни одна мутация не проходит, пока идёт эта гонка, а `rounds` в БД после этого точно совпадает с восстановленным бэкапом. Все переменные вида `TEST_*_DELAY_MS` читаются только тестовым сервером - в production не заданы, задержек нет.

Каждый тестовый файл поднимает свой сервер и свою БД, но сами тестовые процессы (`node --test`) по умолчанию выполняются параллельно - несколько одновременных дочерних серверов и подключений к одному локальному PostgreSQL создают заметную нагрузку и могут приводить к случайным таймаутам. Поэтому `test:integration` запускает файлы последовательно (`--test-concurrency=1`) - дольше, но стабильно.

## Безопасность

- Не добавляйте `.env` в Git.
- Перед первым production-деплоем задайте уникальные `SESSION_SECRET`, пароль админа и пароль БД.
- Если секреты когда-либо попадали в историю Git, сначала смените их на стороне хостинга/БД, затем очистите историю. Удаление файла из новой ветки не отзывает уже раскрытый секрет.
